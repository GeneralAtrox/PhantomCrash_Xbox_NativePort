# Online play without a VPN or port forwarding

Question: can Phantom Crash play online through a relay server we run, without
Radmin VPN or port forwarding, by trying a direct path first and passing packets
through the server when that fails, with players joining by room code? And do
RetroPortingToolKit's `recomp-net` and `recomp-net-server` fit that job?

Short answers:

- **recomp-net: no** for this game. Its server no longer carries game packets at
  all, its session layer is a different netcode from the game's own, and its
  direct-path code owns its own sockets. Details below.
- **A small relay of our own: yes.** It is built on this branch (about 900 lines,
  no new dependencies) and sits under the game's existing socket, so the room,
  handshake, input exchange, rollback prediction and state digests are unchanged.
  Results of the two-machine test are in "Measurements".

## What recomp-net offers, read from its code

Read at `RetroPortingToolKit/recomp-net` and `recomp-net-server`, main branches
as cloned on 2026-11-02.

**Which piece carries game packets when a direct path fails.** The client README,
`docs/architecture.md` and `include/recomp_net/host_relay.h` still describe a
lobby UDP relay (an "SFU") that forwards inputs. The server no longer has one:

- `recomp-net-server` opens no UDP socket at all; `src/main.rs` listens on TCP
  only (WebSocket lobby).
- `src/config.rs` refuses to start when `INPUT_RELAY_ENABLED` is set, with the
  message that server-side match relaying (the UDP SFU) has been removed.
- `HOW_IT_WORKS.md` says the server relays nothing; `WS_LOBBY.md` was amended on
  2026-10-02 to match.

What is left to carry packets is ICE (libjuice) between the players. Only the
one-to-one session (`rnet_session_start_ice`) may use a TURN server, and TURN
is a separate program (coturn) someone has to host. The hub/host-relay ICE
agents are written never to use TURN (`rnet_host_ice.c`, "Never TURN, never
force_relay"; `docs/signaling.md`); when they fail, the match does not start
(`relay_unavailable`, `host_relay_unproven`). So for a game with more than two
players, a player behind a strict NAT has no path at all.

**Session layer.** recomp-net's session is a delay-sync and rollback stack built
around its own input and episode model (`RNetSession`, `RB_*` messages). Phantom
Crash already has its own: `Room` and `ReliablePeer` (handshake with the 32-byte
content digest), the lobby worker, `MatchSession` prediction with rollback, and
state digest agreement. Adopting recomp-net's session would mean replacing all
of that, not reusing it.

**Can it sit under `online_socket`?** Not as it stands. The game's room is a
star on one UDP socket (the host is player 0; clients talk only to it). ICE
agents each own their own socket and need SDP offers and answers passed through
the WebSocket lobby, so they would replace `DatagramSocket` per peer and bring in
the lobby's JSON protocol, sign-in (JWT, optionally Discord), SQLite and the
6,657-line `ws_lobby.rs`. The parts that would really help, STUN-style address
discovery, UPnP/NAT-PMP and hole punching, are small; the relay that the game
actually needs is the part that was removed.

**Licences of what would ship.**

| Piece | Licence | Ships to players? |
| --- | --- | --- |
| recomp-net | MIT | yes, if used |
| libjuice | MPL-2.0 (file-level copyleft: changes to its files must be published) | yes, if used |
| libjuice dependencies | none required; Nettle is optional and off by default | no |
| recomp-net-server and its Rust crates | MIT (server) | no, server only |
| coturn (needed for any TURN relay) | BSD-3-Clause, from its project; not read here | no, server only |
| recomp-net-server `data/ip_country.bin` | generated by `tools/gen_ip_country.py` from its listed sources; check them before deploying | no |
| the relay on this branch | the game's own code | yes |

The relay on this branch adds no third-party code to the game or the server.

**Recommendation.** Our own relay. It is the piece recomp-net no longer has, it
fits the game's one-socket star without touching the netcode above it, it needs
no accounts, database or second server program, and it can be audited in an
afternoon. If later a richer lobby (friends, matchmaking) is wanted, recomp-net's
lobby could sit beside this relay; it would not replace it.

## What was built

All under `port/src/online/` and `port/include/phantomcrash/online_relay.hpp`.

**The server, `phantomcrash_relay.exe`.** One UDP port (default 29650).

```text
phantomcrash_relay [--port 29650] [--seconds N] [--max-rooms 1000]
                   [--test-loss 0.05] [--test-delay-ms 20]
```

- A player says hello; the server answers with a cookie keyed by a secret and the
  player's address, and acts only on requests that carry it. A hello is padded to
  the size of its answer, so the server cannot be used to amplify traffic towards
  a forged address.
- *Create* opens a room and returns a six-character code (32 letters and digits,
  without 0, O, 1 or I). *Join* enters a room by code. Wrong codes are limited to
  20 a minute per IP address; rooms hold four players.
- The server tells each member the others' addresses (as it sees them, plus their
  LAN addresses unless a player chose relay-only) and forwards datagrams between
  members. It never reads the game payload and logs only counts, never addresses.
- Each member may send 256 KB/s through it; more is dropped. A member that has not
  been heard from for 60 seconds is removed, and an empty room closes.
- When a router gives a player a new address, the server answers the stranger
  with *unknown* and the player rejoins its own seat with the room's key.

**The client, `RelayClient`.** It wraps the game's one `DatagramSocket`. The
room addresses other members by made-up addresses (`240.0.0.n:1`), so `Room`,
`ReliablePeer`, the lobby and everything above them do not know which path a
datagram took.

- Every datagram first goes through the server (8-byte header; the socket allows
  for that, so the game's 1,200-byte datagrams still fit).
- At the same time it sends small probes to the other member's addresses, signed
  with the room's key. When a probe is answered, game datagrams switch to that
  direct path. If the direct path hears nothing for two seconds, they go back
  through the server, live, without leaving the match.
- *Relay only* never probes and never tells anyone its address.

**In the game.** Command line only, for now:

```powershell
# host: opens a room and logs "Online room code: ABC234"
phantomcrash_port.exe --root . --online-host 29641 --online-relay RELAY_IPV4:29650
# others
phantomcrash_port.exe --root . --online-relay RELAY_IPV4:29650 --online-room ABC234
```

**The check.** `--online-match-check` runs a real online match with no window
drawn and no real input (the stress-check pilot drives each robot), then prints
round trip, stalls, rollbacks, the path used and the state digest every ten
seconds of game time:

```text
--online-match-check role=host,relay=IP:29650[,relay_only=1][,seconds=120][,loss=0.02][,cut=30]
--online-match-check role=join,relay=IP:29650,code=ABC234[,...]
--online-match-check role=host,port=29641          (plain direct, for comparison)
--online-match-check role=join,direct=IP:29641
```

`loss` drops that share of the game datagrams this copy sends; `cut` stops the
direct path after that many seconds, to prove the fall-back.

**Tests.** `online_relay_tests.cpp` in `phantomcrash_online_tests`: a room plays
through the relay alone with the largest datagram; a different game build is
still refused by the room's own handshake; the direct upgrade and the live fall
back; a wrong code and a full room; a registration without a cookie is ignored.
